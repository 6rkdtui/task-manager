# Task Manager

Task Manager — учебное приложение для управления задачами с двумя интерфейсами: консольным (CLI) и REST API на FastAPI.

Учебный проект создан для закрепления знаний Python, ООП, работы с базами данных, архитектуры приложений и автоматического тестирования.

## Функционал

- создание задачи;
- получение задачи по ID;
- просмотр всех задач;
- изменение задачи;
- отметка задачи выполненной;
- удаление задачи;
- консольное меню;
- обработка некорректного числового ввода;
- хранение задач в PostgreSQL.

## Архитектура

У проекта два интерфейса: консольное меню (`main.py`) и REST API (`api.py`).
Оба используют один и тот же сервис и репозиторий:

| Слой | Ответственность |
| --- | --- |
| `main.py` и `api.py` | Получают ввод пользователя или HTTP-запрос и возвращают результат |
| `TaskService` | Содержит логику работы с задачами |
| `TaskRepository` | Выполняет SQL-запросы к PostgreSQL |
| `Task` | Представляет задачу внутри приложения |

Подключение к PostgreSQL создаётся через `database.py`. Таблица `tasks`
подготавливается при запуске CLI или API, а для тестов — в тестовой фикстуре.
`TaskRepository` работает с уже подготовленной таблицей.

## PostgreSQL

Начиная с версии 0.7, проект использует PostgreSQL вместо SQLite.
Подключение выполняется через драйвер psycopg.
При локальном запуске параметры подключения читаются из .env; при запуске в контейнере они передаются через переменные окружения.

```env
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=task_manager
DB_USER=task_user
DB_PASSWORD=your_password
```

Файл .env не должен попадать в Git.

Таблица tasks содержит:

```text
id
title
description
is_completed
```

Для операций записи используются транзакции:

- commit() после успешной операции;
- rollback() при возникновении ошибки;
- курсоры закрываются после выполнения операций.

## REST API

| Метод | Путь | Действие | Успешный ответ |
| --- | --- | --- | --- |
| POST | `/tasks` | Создать задачу | 201 |
| GET | `/tasks` | Получить список задач | 200 |
| GET | `/tasks/{task_id}` | Получить задачу по ID | 200 |
| PUT | `/tasks/{task_id}` | Обновить название и описание | 200 |
| PATCH | `/tasks/{task_id}/complete` | Отметить задачу выполненной | 200 |
| DELETE | `/tasks/{task_id}` | Удалить задачу и вернуть её данные | 200 |

При создании и обновлении обязательны `title` и `description`.
Пробелы по краям удаляются; пустые строки и строки только из пробелов
не допускаются.

Некорректные входные данные возвращают ответ 422.
Обращение к несуществующей задаче по ID возвращает 404.
Если задач нет, запрос списка возвращает 200 и пустой список.

PUT требует оба поля: `title` и `description`.
Повторное завершение уже выполненной задачи возвращает её
текущее состояние с кодом 200.

Интерактивная документация доступна по адресу `/docs`.

## Тестирование

Для автоматического тестирования проекта используется `pytest`.

Тестами покрыты:

- создание задачи;
- получение задачи;
- получение списка задач;
- обновление задачи;
- частичное обновление задачи на уровне Repository;
- завершение задачи;
- удаление задачи;
- работа с несуществующими задачами;
- получение пустого списка;
- бизнес-логика `TaskService`;
- взаимодействие `TaskService` с Repository через mock-объекты;
- HTTP-эндпоинты API с помощью `TestClient` и подмены `TaskService` через `dependency_overrides`.

Дополнительно сквозной API-тест проверяет создание и получение задачи через настоящий `TaskService`, `TaskRepository` и отдельную PostgreSQL-базу `task_manager_test`.

### Тестирование TaskRepository

Тесты `TaskRepository` работают с отдельной PostgreSQL-базой:

```text
task_manager_test
```

Настройки тестовой базы хранятся в:

```text
.env.test
```

Перед каждым тестом таблица `tasks` очищается, поэтому тесты не зависят друг от друга и не изменяют данные основной базы приложения.

### Тестирование TaskService

`TaskService` тестируется отдельно от реальной базы данных с использованием:

```python
Mock(spec=TaskRepository)
```

Это позволяет проверять бизнес-логику независимо от PostgreSQL.

### Подготовка и запуск всех тестов

Перед запуском полного набора тестов установите зависимости проекта,
создайте отдельную PostgreSQL-базу `task_manager_test`
и подготовьте файл настроек:

```powershell
Copy-Item .env.test.example .env.test
```

Укажите в `.env.test` параметры подключения к тестовой базе.
Пользователь PostgreSQL должен иметь права на создание таблиц
и работу с данными в этой базе.

Тесты очищают таблицу `tasks` в тестовой базе.

Запуск всех тестов:

```powershell
python -m pytest -v
```

## Установка и запуск

Для локального запуска необходимы Python 3.11+ и PostgreSQL.

Клонировать репозиторий и перейти в папку проекта:

```powershell
git clone https://github.com/6rkdtui/task-manager.git
cd task-manager
```

Создать локальный файл настроек из шаблона:

```powershell
Copy-Item .env.example .env
```

Указать в `.env` параметры подключения к своей PostgreSQL-базе.

Создать и активировать виртуальное окружение:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

Установить зависимости:

```powershell
python -m pip install -r requirements.txt
```

Создать базу PostgreSQL `task_manager` и указать параметры подключения в `.env`. Таблица `tasks` будет создана автоматически при запуске приложения, если её ещё нет.

Для запуска консольного приложения:

```powershell
python main.py
```

Для запуска API:

```powershell
python -m uvicorn api:app --reload
```

После запуска API документация доступна по адресу [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs).

## Docker

Из корня проекта можно собрать образ API:

```bash
docker build -t task-manager:0.8 .
```

Для запуска API вместе с PostgreSQL используется Docker Compose.
Нужны установленный Docker Engine или Docker Desktop и Docker Compose.

Из корня проекта создайте `.env` из шаблона.

В Linux:

```bash
cp .env.example .env
```

В Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

Если `.env` уже настроен, используйте существующий файл.

Укажите в `.env` значения `DB_NAME`, `DB_USER` и `DB_PASSWORD`.
Compose передаст их контейнерам PostgreSQL и API.
Адрес базы для API внутри Docker-сети задан в `compose.yaml` как `DB_HOST=db`.

При первом запуске с пустым томом контейнер PostgreSQL автоматически
создаст пользователя и базу. Создавать основную базу вручную
для этого способа запуска не требуется.

Собрать и запустить сервисы:

```bash
docker compose up --build -d
```

После запуска документация API доступна по адресу `http://127.0.0.1:8000/docs` на машине, где работает Docker.

Остановить сервисы:

```bash
docker compose down
```

Эта команда удаляет контейнеры и сеть проекта, но сохраняет задачи в именованном томе PostgreSQL.

Локальные `.env` и `.env.test` исключены из образа через `.dockerignore`. Compose читает `.env` на машине запуска и передаёт нужные значения контейнерам.
